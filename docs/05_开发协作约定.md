# 开发协作约定（Shadow Cube）v1.0

> 目标：**改得动、跑得起来、留得下痕迹**
> 适用：本仓库所有代码、配置、文档变更

---

## 1. 核心约定（必须遵守）

> **完成「较大调整」后，自动进行体检，体检通过则提交并推送到远端。**

### 1.1 什么算「较大调整」

满足**任意一条**即触发体检 + 提交推送流程：

| 类型 | 示例 |
|---|---|
| 新增/重构模块 | 打包管线、混淆模块、玩法核心系统 |
| 引擎/环境变更 | Unity 版本、渲染管线、构建配置、包名 |
| 新增文档或大段修订 | 新增 `docs/0x_*.md`、重写章节 |
| 公共配置变更 | `BuildConfig/build.json`、`.gitignore`、`.gitattributes` |
| 影响构建的设置 | Player Settings、包依赖、脚本后端 |
| 里程碑完成 | M0 / M1 / … 任一阶段收尾 |

**不触发**（可先攒着）：单行文案修正、注释调整、临时调试文件（且未入库）。

### 1.2 体检内容

执行 `./tools/healthcheck.sh`（可选 `--build` 追加一次联调包构建）：

1. **工具链**：git / git-lfs / Unity 是否就绪，`BuildConfig/build.json` 是否存在
2. **编译**：Unity 无头编译 C#，出现 `error CS` 即失败
3. **Git 卫生**：
   - 密钥类文件（keystore / jks / key）不得入库
   - 大于 5 MB 的文件必须走 LFS（依据 `.gitattributes`）
   - 提示未跟踪文件，确认是否遗漏入库
4. **文档同步**：`docs/01~08` 齐全
5. **统计台账**：自动统计测试条数 / 代码行数 / 问题条数，与文档中的托管标记比对，过期则告警（详见 §8）
6. **（可选）构建验证**：跑一次 `./tools/build.sh debug`

退出码：`0` 通过（可提交推送）／`1` 失败（先修复）。

### 1.3 流程

```
较大调整完成
   ↓
体检 ./tools/healthcheck.sh
   ↓ 通过
提交（Conventional Commits）
   ↓
推送 git push origin main
   ↓
向用户汇报：提交号 + 变更清单 + 体检结论 + 遗留项
```

**体检未通过时禁止推送**，先修复并重新体检。

## 2. 提交规范

采用 [Conventional Commits](https://www.conventionalcommits.org/)：

```
<type>(<scope>): <简述>

<body：为什么改、改了什么、影响面>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 / 新模块 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档 |
| `refactor` | 重构（无功能变化） |
| `perf` | 性能优化 |
| `build` | 构建/打包/依赖 |
| `chore` | 杂项（忽略规则、脚手架） |

示例：

```
feat(build): 打包管线加入可开关的代码混淆

- 新增 ShadowCubeObfuscation：IL2CPP 前处理托管 DLL
- level 0/1/2/3 可配置，联调包强制关闭
- 文档：03 新增 §5、04 新增 TC-BUILD-13~18
```

**提交粒度**：一个逻辑变更一次提交，禁止把无关改动混在一起。

## 3. 分支与推送

| 项 | 约定 |
|---|---|
| 主分支 | `main`（唯一长期分支） |
| 日常开发 | 直接在 `main`；里程碑大改可开 `feature/*`，合并后删除 |
| 推送时机 | 体检通过后立即推送，避免本地堆积 |
| 禁止 | `push --force`、`--no-verify`、绕过钩子 |

## 4. 安全红线

- ❌ 绝不提交：`*.keystore`、`*.jks`、`*.key`、`BuildConfig/keystore.json`（已在 `.gitignore`）
- ❌ 绝不提交：构建产物 `Builds/`、Unity 缓存 `Library/`、`.utmp/`
- ❌ 绝不在日志/文档/提交信息中出现密钥、口令、令牌
- ✅ 大文件（贴图/音频/模型/字体）必须经 Git LFS（规则见 `.gitattributes`）

## 5. 文档同步约定

改动涉及下列内容时，**同一次调整必须同步更新对应文档**：

| 变更 | 需更新文档 |
|---|---|
| 环境 / 版本 / 包名 | `02_开发环境文档.md` |
| 打包 / 签名 / 发布 | `03_打包发布流程文档.md` |
| 影响玩法或验收标准 | `01_需求文档.md` + `04_测试文档.md` |

| **测试条数 / 代码规模 / 问题条数** | ❌ **禁止手改**，由 `tools/healthcheck.sh --sync-docs` 回写（见 §8） |

## 7. 问题沉淀约定（强制）

> **开发或测试过程中出现的任何问题，必须沉淀到 `06_开发总结.md`，不能只修不记。**

### 7.1 什么时候记

满足任意一条即记录：

- 排错耗时 **> 10 分钟**（环境、工具链、网络、API 变更）
- 报错信息**看不懂 / 与直觉相反**（如 fake-null、废弃 API、Awake 顺序）
- **测试断言与实现相互打脸**（说明有一方对业务理解错了）
- 同一个坑**第二次出现**

### 7.2 记录要求

1. 按 `06_开发总结.md` §1 的格式写：现象 / 原因（**要带证据**：日志、实测重定向、报错原文）/ 解决 / 沉淀。
2. **必须提炼成「测试 / 工具 / 约定」三者之一**，不能只写"已修复"：
   - → **测试**：加一条 EditMode 或 PlayMode 用例，防回归
   - → **工具**：写进 `tools/healthcheck.sh` / 打包脚本 / 编辑器菜单，让工具替人记住
   - → **约定**：写进本文档或 `docs/02/03`，变成团队规范
3. 修 bug 的提交信息中带上问题编号，例如 `fix: 修正 fake-null 判空（PROB-CODE-01）`。

### 7.3 动手前的反向使用

- **开始一个不熟悉的操作前，先搜 `06_开发总结.md`**（Unity 批处理、Gradle、签名、混淆、磁盘 等主题），避免重复踩坑。
- 体检脚本已把高频坑转成自动检查（编译、单测、Git 卫生、LFS、磁盘），能自动发现的就不靠人记。

## 6. 常用命令速查

```bash
./tools/healthcheck.sh            # 快速体检（编译 + EditMode/PlayMode + Git 卫生 + 文档 + 统计）
./tools/healthcheck.sh --build    # 完整体检（额外跑一次联调包构建）
./tools/healthcheck.sh --skip-tests  # 只查编译与环境（测试条数沿用上次结果）
./tools/healthcheck.sh --sync-docs   # 把自动统计值回写文档（改完需提交）
./tools/build.sh debug            # 打联调测试包（APK，真机+模拟器）
./tools/build.sh release          # 打正式包（AAB，签名）
git add -A && git commit -m "..."  # 提交（Conventional Commits）
git push origin main              # 推送
```

### 7.4 踩坑速查索引（详见 `06_开发总结.md`）

| 主题 | 关键结论 |
|---|---|
| 装依赖 | brew 可能不可用 → 优先官方二进制；GitHub 文件名先用 API 查 |
| Unity 下载/登录 | 被地域路由到 unity.cn 时，换国际出口网络 |
| 许可证 | Unity 6 无 `.ulf`，看 Editor.log 的 `License group` |
| 批处理 | 先关 GUI 编辑器；任务串行；后台跑 + 轮询结果文件 |
| 代码 | 禁止对 `UnityEngine.Object` 用 `??` / `?.`（fake-null） |
| 编辑器 API | 废弃名先在 `UnityEditor.CoreModule.dll` 里 grep 确认 |
| 状态变更 | 只允许一个入口（公开 API），避免漏触发判定 |
| 断言失败 | 先自证业务预期，再怀疑代码 |
| 统计数字 | 由脚本托管，禁止手改（见 §8） |

## 8. 统计数字托管约定（强制）

> **动机**：手写汇总表必然腐化。本项目已多次出现同一事实多处不一致 ——
> 测试条数 `04`=99 / `06`=73 / 实测 135；LFS 安装路径 `02` §5.1 与 §10 不一致；`06` §5 合计与明细不符。
> 详见 `08_AI游戏项目经验沉淀.md` §4.8「文档腐化自检清单」。

### 8.1 哪些数字交给机器

| 托管项 | 出现位置 | 统计口径实现 |
|---|---|---|
| EditMode / PlayMode 用例数、总条数 | `04` §6.1、`06` §3.4 | Test Framework 结果 XML 的 `total` |
| C# 总行数 / 运行时行数 / 测试行数 / 测试占比 | `04` §6.1 | `Assets` 下 `*.cs` 行数 |
| 各类问题条数与合计 | `06` §5 | `06` §2 中 `PROB-*` 编号去重统计 |

### 8.2 规则

1. 被托管的数字在文档中用 `<!-- STAT:名称 -->值<!-- /STAT:名称 -->` 包裹，**禁止手改**；
2. 体检脚本每次运行自动比对，不一致即告警（不阻断，除非有失败项）；
3. 需要同步时执行 `./tools/healthcheck.sh --sync-docs`，**回写后必须提交**；
4. 新增可被机器统计的数字时，在文档中加标记并在 `tools/stats.py` 中登记口径；
5. **叙述性文字中不要重复硬编码这些数字**（如「共 99 条测试」），改为引用 §6.1 的托管值或写「见 §6.1」。
