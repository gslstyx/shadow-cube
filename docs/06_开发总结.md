## 2. 问题清单

### 2.1 环境与工具链

**【PROB-ENV-01】Homebrew 无法安装任何包**
- 现象：`brew install git-lfs` 报一堆 Ruby 语法错误（`def openssldir = pkgetc`）。
- 原因：Homebrew 4.0.26 自带 Ruby 2.6，无法解析新 formula 的 Ruby 3.x 语法。
- 解决：绕开 brew，用官方二进制安装（下载 zip → 拷贝 `git-lfs` 到 `/usr/local/bin` → `git lfs install`）。
- 沉淀 → **约定**：环境依赖优先用官方二进制/安装包，`docs/02` 记录。

**【PROB-ENV-02】GitHub Release 下载失败**
- 现象：直连 `github.com/.../releases/download/...` 超时（exit 56）；多个代理镜像返回 403/404。
- 原因：网络出口受限。
- 解决：切到国际出口后成功；且**文件名猜错会 404**（正确为 `git-lfs-darwin-amd64-v3.8.0.zip`，带 `v`）。
- 沉淀 → **约定**：下载前先用 GitHub API 列出 `assets[].name`，不要凭记忆拼文件名。

**【PROB-ENV-03】Unity 下载被"地域路由"到 Unity 中国**
- 现象：`unity.com/download` → 302 `unity.cn/releases`；`public-cdn.cloud.unity3d.com` → 307 `public-cdn.cloud.unitychina.cn`；Hub 登录跳到 `id.unity.cn`。
- 原因：Unity 按 IP 所在地分流中国大陆用户到 Unity 中国（unity.cn / 团结引擎）体系。
- 解决：使用非中国大陆出口网络；先验证 Hub 是国际版（`app.asar` 内嵌 `id.unity.com` / `download.unity3d.com`，无 `unitychina`）。
- 沉淀 → **工具**：`docs/02 §5.4` 记录实测证据与判断方法。

**【PROB-ENV-04】误判"许可证未激活"**
- 现象：找不到 `Unity_lic.ulf`，以为没激活。
- 原因：**Unity 6 不再生成 `.ulf` 文件**，许可证由 Licensing Client 管理。
- 解决：以 Editor 日志为准：`[Licensing::Module] License group: Product: Unity Personal / Expiration: Unlimited`。
- 沉淀 → **约定**：判断引擎状态要看日志证据，不依赖旧版本文件特征。

**【PROB-ENV-05】CLI 建工程不是 URP**
- 现象：`-createProject` 出来的工程 `m_CustomRenderPipeline: 0`，manifest 无 URP。
- 原因：CLI 创建的是空 3D（Built-in）工程，不走模板。
- 解决：手动加 `com.unity.render-pipelines.universal`，再用编辑器脚本创建 `UniversalRenderPipelineAsset` + RendererData 并写入 `GraphicsSettings` / `QualitySettings`。
- 沉淀 → **工具**：`ShadowCubeUrpSetup.cs`（一次性脚本）；`docs/02 §5.3` 记录。

**【PROB-ENV-06】批处理下不生成 `.sln`**
- 现象：装了 `com.unity.ide.vscode` 后仍无 `ShadowCube.sln`；日志显示 `CurrentEditor = UnityEditor.DefaultExternalCodeEditor`。
- 原因：batchmode 下 Unity 未把 VS Code 识别为外部编辑器（plist 里 `kScriptEditor` 已设置但未生效）。
- 解决：在编辑器脚本中显式 `CodeEditor.SetExternalScriptEditor(path)` 后再 `SyncAll()`。
- 沉淀 → **工具**：菜单 `Tools → Shadow Cube → 1) 生成 IDE 工程文件`。

**【PROB-ENV-07】Unity 编辑器打开工程会阻塞批处理**
- 现象：`-batchmode` 运行被静默中止，日志只到 "Successfully changed project path"；另一次报 "It looks like another Unity instance is running with this project open"。
- 原因：同一工程不允许两个 Unity 实例。
- 解决：跑批处理前先关闭 GUI 编辑器（`osascript quit` → 必要时 `pkill`）。
- 沉淀 → **工具**：`tools/healthcheck.sh`、构建脚本运行前先确认无其它实例；连续批处理任务必须**串行**。

**【PROB-ENV-08】磁盘空间被低估**
- 现象：装 Editor + Android 模块后可用空间从 40GB 掉到 17GB。
- 原因：Editor ~19GB + SDK/NDK/JDK ~4GB + 构建中间产物（IL2CPP/Gradle）。
- 解决：清理（Docker、微信、视频缓存、废纸篓）；构建前保证 ≥15GB。
- 沉淀 → **工具**：`docs/03` 构建前检查清单已含磁盘项；`healthcheck` 输出体积提示。

**【PROB-BUILD-01】Shader.Find 在真机/模拟器上返回 null（编辑器正常）** ⭐ 设备冒烟抓到的第一个真 bug
- 现象：模拟器上 3D 场景整体缺失（黑屏，只有 UI），日志 `ArgumentNullException: Parameter name: shader`，位于 `GameController.CreateMaterial`。
- 原因：运行时 `Shader.Find("Universal Render Pipeline/Lit")` 只能找到**被打包引用过**的 shader；材质全部由代码在运行时创建，没有任何资产引用该 shader → 打包时被剔除。编辑器里资源齐全所以一直正常。
- 解决：改为**材质资产引用**——新增菜单 9) 生成运行时材质资产（`Assets/Materials`），场景生成器把材质赋给各组件的序列化引用；代码仅保留回退路径并打警告。
- 沉淀 → **约定**：禁止运行时用 `Shader.Find` 创建正式材质，统一走材质资产；→ **测试**：设备冒烟进入固定流程（首屏截图必须能看到 3D 内容）。

**【PROB-BUILD-02】Build Settings 场景顺序被 M1SceneBuilder 插到最前**
- 现象：模拟器启动直接进入游玩场景，而不是首页。
- 原因：`M1SceneBuilder.AddToBuildSettings` 用 `Insert(0, …)` 把游玩场景抢占了启动位。
- 解决：改为追加到末尾；场景顺序统一由 `MenuSceneBuilder` 维护（首页 → 选关 → 游玩）。
- 沉淀 → **约定**：Build Settings 顺序只由 `MenuSceneBuilder` 一个入口维护。

**【PROB-ENV-09】安全策略拦截删除操作**
- 现象：`rm` / `shutil.rmtree` 删除工作区外文件时报 Node 语法错误（safe-delete guard 拦截），文件未删。
- 原因：IDE 安全删除钩子（Node v10 不兼容其脚本）。
- 解决：改用 `mv` 到废纸篓，或交由用户手动删除。
- 沉淀 → **约定**：清理工作区外文件默认改用 `mv ~/.Trash/`。

**【PROB-ENV-10】Unity 6 的启动 Activity 类名已改名**
- 现象：`adb shell am start -n com.gslstyx.shadowcube/com.unity3d.player.UnityPlayerActivity` 报 `Error type 3: Activity class ... does not exist`。
- 原因：Unity 6 生成的启动 Activity 是 **`com.unity3d.player.UnityPlayerGameActivity`**（不是 UnityPlayerActivity）。
- 解决：装机脚本/命令改用新类名；不确定时可先 `adb shell dumpsys activity activities | grep mResumedActivity` 看实际类名，或用 `adb shell monkey -p <包名> 1` 启动。
- 沉淀 → **约定**：真机启动统一用 `monkey -p` 或先查询实际 Activity 名，不写死类名。

### 2.2 Unity API 与代码坑

**【PROB-CODE-01】`GetComponent<T>() ?? AddComponent<T>()` 是错的**（最高价值）
- 现象：PlayMode 12 个测试全挂，报 `MissingComponentException: There is no 'AudioSource' attached`。
- 原因：`UnityEngine.Object` 的 **fake-null** 不参与 `??` 判断，`GetComponent` 返回的"假 null"不会触发 `AddComponent`。
- 解决：统一改为 `var c = GetComponent<T>(); if (c == null) c = gameObject.AddComponent<T>();`（本次修了 3 处）。
- 沉淀 → **测试**：PlayMode 音效/轨迹测试即回归防线；**约定**：禁止对 `UnityEngine.Object` 使用 `??` / `?.`。

**【PROB-CODE-02】Unity 6 一批 API 已废弃/改名**

| 旧写法 | 现象 | 新写法 |
|---|---|---|
| `GraphicsSettings.renderPipelineAsset` | CS0618 废弃 | `GraphicsSettings.defaultRenderPipeline` |
| `PlayerSettings.SetScriptingBackend(BuildTargetGroup, …)` | CS0618 | `SetScriptingBackend(NamedBuildTarget, …)` |
| `EditorUserBuildSettings.developmentBuild` | CS0117 不存在 | `BuildOptions.Development` |
| `AndroidMinification` / `androidReleaseMinification` | CS0619 废弃 | `PlayerSettings.Android.minifyRelease / minifyDebug / minifyWithR8` |
| `BuildReport.files` | CS0619 废弃 | `report.GetFiles()`（`BuildFile` 是 struct，不能 `== null`） |
| `NewSceneSetup.Empty` | CS0117 不存在 | `NewSceneSetup.DefaultGameObjects`（复用自带相机/灯光） |

- 沉淀 → **约定**：升级引擎/写编辑器脚本时，先在 `UnityEditor.CoreModule.dll` 里 `strings | grep` 确认 API 名，别猜。

**【PROB-CODE-03】缺 using 导致 CS0103/CS0104**
- `NamedBuildTarget` → 需 `using UnityEditor.Build;`
- `GraphicsDeviceType` → 需 `using UnityEngine.Rendering;`
- `Debug` 二义性（`System.Diagnostics` vs `UnityEngine`）→ 加别名 `using Debug = UnityEngine.Debug;`
- 沉淀 → **约定**：编辑器脚本模板统一带上这两个 using。

**【PROB-CODE-04】接口方法名写错**
- 现象：`IPostprocessBuildWithReport` 实现报 CS0535。
- 原因：接口方法名是 `OnPostprocessBuild(report)`，我写成了 `OnPostprocessBuildWithReport`。
- 沉淀 → **约定**：实现 Unity 回调接口前先看接口签名。

**【PROB-CODE-05】碰撞体延迟销毁会挡一帧射线**
- 现象：悬停方块/投影 quad 的碰撞体用 `Destroy` 后，当帧仍会拦截 `Physics.Raycast`。
- 解决：先 `collider.enabled = false`，再 `Destroy`。
- 沉淀 → **约定**：运行时移除碰撞体一律"先禁用再销毁"。

**【PROB-CODE-06】Awake 执行顺序不可依赖**
- 现象：`GameController.Awake` 使用 `CameraRig.WallsRoot` 时可能为 null（组件 Awake 顺序未定义）。
- 解决：属性懒创建（`EnsureWallsRoot()`）。
- 沉淀 → **约定**：跨组件初始化一律懒加载/显式初始化，不依赖 Awake 顺序。

**【PROB-CODE-07】其它组件 Awake 更早 → 读到未初始化服务（同一个坑，第二次出现）**
- 现象：PlayMode 32 个用例全挂，`NullReferenceException` at `ProgressManager.GetStars ← GameHud.Refresh ← GameHud.Awake`。
- 原因：`GameHud.Awake` 早于 `ProgressManager.Awake` 执行，`Progress`（进度服务）尚未创建；组件引用是场景里赋好的（非空），但内部服务是空的。
- 解决：`ProgressManager` 的 `Data` / `Progress` 改为**首次访问时懒加载**（`EnsureReady()`）。
- 沉淀 → **约定**：对外暴露的服务/数据一律"懒加载 + 属性访问"，不假设自身 Awake 先执行；**同一根因第二次出现，已列入重点检查项**。

**【PROB-CODE-08】UI 在 Awake 里抓到"即将被销毁的重复单例"（同根因第三次）**
- 现象：PlayMode `点击关卡_进入游玩场景且载入该关卡` 失败，点击按钮后场景不变（仍在 LevelSelect）。
- 原因：跨场景单例 `LevelFlow` 用 `DontDestroyOnLoad` + 重复实例销毁；`LevelSelectUI.Awake` 用 `FindObjectOfType` 抓到的可能是**本场景那个即将被销毁的重复实例**，缓存后变成 fake-null → 点击时 `flow == null` 直接 return。
- 解决：UI 改为**使用时懒解析**（`Flow => flow != null ? flow : (flow = FindObjectOfType<LevelFlow>())`），利用 Unity fake-null 自动重找；`GameHud` / `SettlementPanel` 同步处理。
- 沉淀 → **约定**：`DontDestroyOnLoad` 单例的引用**禁止在 Awake 缓存**，一律使用时解析；**该根因已第三次出现（PROB-CODE-06/07/08），列为 Unity 项目第一高危坑**。

**【PROB-RENDER-01】Unity 内置 Quad 网格正面朝 -Z，两面投影墙被背面剔除（画面里"看不到墙"）** ⭐ 最隐蔽的一处
- 现象：Game 视图里只有平台，**两面墙与墙面投影完全看不到**；但对象确实存在、`activeSelf=true`、`GeometryUtility` 判定在视锥内、材质/颜色/渲染队列都正常。
- 排查：无头渲染 + 对照物（同材质的新建 Quad / 新建 Cube）→ **Cube 正常显示，Quad 完全不画**；再把墙面材质强制成不透明红色，依然不可见 → 排除"半透明太淡 / 混合失效"。
- 原因：`PrimitiveType.Quad` 的网格**可视面法线朝 -Z**（不是 +Z）。墙面局部 +Z 是指向相机的法线，`transform.forward` 指向相机 ≠ 可视面朝相机 → 整片面被**背面剔除**。
- 解决：`ProjectionWallView` 中所有投影面绕 Y 轴转 180°（`QuadFacing`）；同时 `MaterialUtils.SetTransparent` 统一 `_Cull = 0` 作为双面兜底。
- 沉淀 → **测试**：原用例只断言"激活 + 在视锥内"，属于**假通过**；新增像素级用例 `墙面与投影块_必须真的被渲染出来`（渲染一帧后采样墙面/投影块像素，必须显著区别于背景色）。→ **约定**：凡"看得见/看不见"类需求，一律做**渲染像素断言**，禁止只用对象状态断言。

**【PROB-RENDER-02】半透明面板被排到投影之后绘制，把投影整片糊掉（透明排序）**
- 现象：把墙面改成**灰白**后，目标投影只剩一格；像素采样显示投影块像素 `(0.702)` ≈ 墙面像素 `(0.698)`（深色面板时不易察觉，浅色面板立刻暴露）。
- 原因：透明队列按**渲染器包围盒中心**到相机的距离排序。面板面积大、中心比底部的投影格更靠近相机 → 面板被排在**之后**绘制，且两者都不写深度（`ZWrite=0`），面板就叠在了投影上方。
- 解决：显式分层渲染队列 —— 面板 `2900` → 边框 `2920` → 投影块 `3000`（`ProjectionWallView` 在克隆材质时写入）。
- 沉淀 → **测试**：新增"目标投影像素必须比墙面更深"断言；**约定**：同一处有多层半透明面片时，必须显式指定 `renderQueue`，不要依赖默认排序。

### 2.3 逻辑与测试

**【PROB-LOGIC-01】公开 API 未触发过关检查**
- 现象：PlayMode 测试 `搭建标准解_过关且为五星` 失败（`IsSolved=false`）。
- 原因：过关检查只写在输入路径 `Apply()` 里，公开的 `AddAt/RemoveAt` 没有。
- 解决：把检查下沉到 `AddAt/RemoveAt` 内部，输入路径复用同一套 API。
- 沉淀 → **测试**：玩法链路测试常驻；**约定**：状态变更逻辑只允许有一个入口。

**【PROB-TEST-01】测试断言写错（代码是对的）**
- 现象：`旋转180度_使用与0度相同的表` 失败。
- 原因：我误以为 180° 时镜像应相同；实际从对侧看墙，x 方向相反，**镜像本就该相反**。
- 解决：修正断言，并补 `旋转360度_复原` 用例。
- 沉淀 → **约定**：断言失败先自证"业务预期是否写错"，再改代码。

**【PROB-TEST-02】PlayMode 测试用例与场景关卡不一致**
- 现象：`通关关卡后_结算记录进存档` 用固定目录（L1/L2/L3）跑场景关卡，导致 `RecordResult` 被"非目录关卡忽略"规则吞掉。
- 解决：测试内用场景真实关卡重建 `LevelCatalog`。
- 沉淀 → **约定**：涉及目录/ID 的测试必须与真实数据源一致。

**【PROB-TEST-04】测试间共享存档状态导致断言不稳**
- 现象：`星级显示_读取存档中的最好成绩` 失败——期望 "4"，实际 "5/5"。
- 原因：同一次 PlayMode 运行中，前面的用例（过关结算）已把 5 星写进**同一份真实存档**（`persistentDataPath`），且星级取最好 → 后续用例的 4 星无法生效。
- 解决：断言前显式 `ResetProgress()` 归零，再写入期望值。
- 沉淀 → **约定**：涉及持久化的用例**必须先重置状态**，不依赖执行顺序；后续考虑给测试注入内存存储替代真实文件。
- 现象：手工 grep 日志容易漏判（"无结果文件"≠"通过"）。
- 解决：统一用 `-testResults` 输出 XML + python 解析 `total/passed/failed`，并把"结果文件是否存在"作为失败信号。
- 沉淀 → **工具**：`tools/healthcheck.sh` 的 `[2.5]`。

## 3. 流程经验（可复用）

### 3.1 开发节奏（设备冒烟已纳入流程）
1. **纯逻辑先行**：把判定/投影/进度等写成不依赖场景的类（`ShadowCube.Core`）→ 先跑 EditMode 单测，再进 PlayMode 和场景。
2. **骨架先跑通**：任何大模块都先做"能被自动化验证的最小闭环"（如先 API + 测试，再做表现）。
3. **一次只推进一层**：环境 → 数据 → 表现 → UI；每层收尾都体检 + 推送。
4. **大调整后固定动作**：`healthcheck.sh` → `commit` → `push`（见 `docs/05`）。

### 3.2 批处理 Unity 的可靠用法
- 同一工程**只能有一个实例**；批处理任务必须串行，且先关 GUI 编辑器。
- 长任务用 `nohup ... &` 后台跑，**轮询结果文件**（`-testResults` XML / 构建产物 / `last-build.txt`）判断完成，而不是盲等。
- 日志统一落到 `/tmp/<task>.log`，用 `grep -E "error CS|\[ShadowCube\]"` 快速判定。
- 构建/测试超时经验值：EditMode ~1–2 分钟；PlayMode ~2–3 分钟；双架构 IL2CPP AAB **17–23 分钟**。

### 3.3 证据优先论
- 判断"是否激活/是否国际版/是否生效"，一律**看日志与实测重定向**，不看旧版本经验（`PROB-ENV-03/04` 就是反例）。
- 报错先看第一条 `error CS`（后面的常是连锁错误）。

### 3.4 测试优先的投资回报
- 本次 3 个真 bug（`PROB-CODE-01`、`PROB-LOGIC-01`、`PROB-CODE-05`）**全部由自动化测试/回归发现**，而不是靠肉眼。
