## 0. 一页纸速查（TL;DR）

### 0.1 二十条通用经验（G1~G20）

> 带 `[U]` 者为 Unity/Unity 生态特有，其余与引擎无关。

| # | 经验 |
|---|---|
| **G1** | 先写不依赖引擎的**纯逻辑层**，让最容易错的部分第一天就被单测覆盖 |
| **G2** | 模块的交付物是「**能被自动验证的最小闭环**」，不是「功能写完」 |
| **G3** | 一次只推进一层：**环境 → 数据 → 表现 → UI/内容**，禁止跳层 |
| **G4** | 大改动后的固定动作：**体检 → 提交 → 推送 → 汇报四要素**（提交号/变更/体检结论/遗留） |
| **G5** | 每个坑必须落成 **测试 / 工具 / 约定** 三者之一，否则下一次会话必然重犯 |
| **G6** | 同类问题**第二次出现时产出通用禁令**，不要再修一次具体位置 |
| **G7** | 断言失败**先自证业务预期**，再怀疑代码（本项目中代码是对的、断言是错的） |
| **G8** | 「看得见」类需求一律**像素/渲染断言**；对象状态断言会假通过（对象全在但屏幕空白） |
| **G9** | 只在真机暴露的问题（资源剔除、架构、性能）必须有**设备冒烟**兜底 |
| **G10** | **运行时动态创建/查找**的资源依赖最脆，一律改为资产化 + 静态引用 `[U]` |
| **G11** | **状态变更只允许一个入口**；输入路径与对外 API 复用同一入口 |
| **G12** | 框架对象的「空」语义可能与语言直觉不符，**禁用语言级空运算符**处理框架对象 `[U]` |
| **G13** | 不依赖组件初始化顺序；跨对象引用**懒加载 + 使用时解析** `[U]` |
| **G14** | 会被调的数值不许写死，全部数据化（配置/ScriptableObject/关卡数据） |
| **G15** | 将来要接的外部服务，第一天就**定义接口 + 空实现**，逻辑层永不被阻塞 |
| **G16** | 帧率/内存/包体/启动等预算**在需求阶段写死数字**，否则后期无仲裁标准 |
| **G17** | AI 只能验证「在不在 / 对不对」；「好不好玩 / 好不好看」留给人类拍板 |
| **G18** | 文档要**单一事实源**；能被机器统计的数字一律交给机器（§4.2） |
| **G19** | 需求要有**稳定编号 + 差距审计表**，让「文档反哺开发」成为机制而非偶然 |
| **G20** | **加约束只能让游戏更难，加动词才能换玩法**；每个新机制需 5~10 关教学容量 |

### 1.1 事实账本

| 项 | 值 |
|---|---|
| 规模 | 3 天 / 27 次提交 / C# 8,144 行，**测试占 32.6%** |

| 沉淀 | 26 条问题，每条落到测试/工具/约定之一 |

### 1.2 做对了 / 没做好

| 做对了（ROI 排序） | 没做好（后果） |
|---|---|
| 纯逻辑先行 → 核心算法第一天就有回归防线 | **需求与实现静默退化**：需求写「真 3D 体素」，实现实为「高度图」，测试全绿无人察觉（§6.1） |

| 沉淀三选一 → 同根因问题第三次被抽象成禁令 | **编号污染**：需求文档出现两组 §8.3/§8.4，交叉引用失效 |
| 差距审计表 → 最后一天 5 次提交全部由它催生 | **统计表腐化**：合计与明细不符、编号跳号 → 已由 §4.2 机器托管解决 |
| 设备冒烟 + 无头截图 → 抓住 shader 被剔除 | 混淆 level≥2、中文字体子集化未验证（已登记 §8.3） |

### 1.3 真正的产出：三条可复用产线

1. **工具产线**：体检 + 一键打包 + 统计台账（`tools/stats.py`）
2. **文档产线**：8 篇职责单一、带锚点引用的文档 + 差距审计表 + TC↔自动化映射
3. **规范产线**：Conventional Commits + 体检通过才推送 + 安全红线 + 问题必沉淀

> 只复制这三样，也能省掉约 60% 的「重新踩坑」成本。

## 2. 开发流程：四层推进法

```
① 环境层   Engine/SDK/打包/体检脚本   → 能一键出包
② 数据层   纯逻辑：结构+算法+判定     → EditMode 全绿
③ 表现层   场景/相机/材质/动效        → PlayMode 全绿 + 无头截图
④ UI·内容层 菜单/HUD/结算/引导/关卡   → 手工用例 + 设备冒烟
```

**铁律**：每层交付「可自动验证的最小闭环」；每层收尾 `healthcheck → commit → push`；**禁止跳层**（在 UI 里写业务逻辑 = 返工之源）。

**单模块循环**
```
需求条款 → 最小 API + 单测(红) → 实现(绿) → 表现接入(截图自证)
        → 体检 → Conventional Commit → push
        → 汇报：提交号 / 变更清单 / 体检结论 / 遗留项
```

**里程碑收尾两件事**：① 需求差距审计（§4.4）；② 按 `05` §5 同步文档，同批提交完成。

**AI 角色边界**

| 交给 AI | 必须人来做 / 拍板 |
|---|---|
| 纯逻辑+单测、编辑器工具、批处理脚本、文档起草 | 引擎安装与许可证、设备调试与上架、商业合规决策 |
| 出方案备选项 | **视觉观感、手感、难度曲线**（AI 无法验证） |

**节奏基线**（Intel i7/16GB）：EditMode 1~2 min ｜ PlayMode 2~3 min ｜ 无头截图 ~1 min ｜ 双架构 IL2CPP APK 23 min ｜ AAB 17 min ｜ 构建前磁盘 ≥15GB。

**批处理铁律**：同一工程只允许一个引擎实例（先关 GUI）→ 任务串行 → `nohup` 后台 + 轮询结果文件（不 sleep 盲等）→ 测试用 `-testResults` XML 判成败（结果文件不存在 = 失败）→ 报错只看第一条 `error CS`。

## 3. 问题与预防（按根因聚类，不按现象记）

### 3.1 五类根因

| 类 | 根因 | 典型表现 | 通用化解法 |
|---|---|---|---|
| **A 生命周期** `[U]` | 框架对象空语义特殊 + 初始化顺序未定义 | `GetComponent<T>() ?? AddComponent<T>()` 无效；`Awake` 读到未初始化服务；缓存到即将销毁的重复单例 | 禁 `??`/`?.`；单例引用**使用时解析**；初始化懒加载 |
| **B 资产打包** | 运行时动态引用在精简打包时被剔除 | 材质运行时 `Shader.Find` → 真机整屏缺失（编辑器正常） | 资产化 + 静态引用；**设备冒烟兜底** |
| **C 渲染可见** | 「对象存在」≠「画出来了」 | Quad 可视面朝 -Z 被背面剔除；透明排序导致大面板盖住投影 | **像素断言**；显式 `renderQueue`；双面兜底 |
| **D 版本漂移** | 引擎/SDK API 废弃改名 | Unity 6 中 7 处 API 变更、启动 Activity 改名 | 写脚本前先在目标版本 DLL 里 grep 确认 API 名 |
| **E 入口分裂** | 同一状态变更有多条路径 | 过关判定只写在输入路径，公开 API 没触发 | **状态变更唯一入口** |

> A 类在本项目**同根因犯了 3 次**：前两次只修外形，第三次才抽象成禁令 —— 这就是 G6 的来源。

### 3.2 最高价值五条

1. **断言失败先自证业务预期**（180° 镜像本就该相反，是断言错了，改代码会毁掉正确实现）
2. A 类禁令（fake-null / 单例缓存 / Awake 顺序）
3. **可见性一律像素断言**
4. **禁运行时 `Shader.Find` 创建正式材质**
5. **每个坑必须落到测试/工具/约定**

### 3.3 沉淀「三选一」机制

**触发即记**：排错 >10 分钟 ｜ 报错看不懂/反直觉 ｜ 测试与实现互相打脸 ｜ 同一坑第二次出现。

**落点三选一**：→ **测试**（加用例防回归）｜→ **工具**（写进体检/打包脚本/编辑器菜单）｜→ **约定**（写进规范文档）。
提交信息带编号：`fix: 修正 fake-null 判空（PROB-CODE-01）` —— 让 `git log` 成为可索引经验库。

### 3.4 八条硬禁令（抄进 `AGENTS.md`）

```markdown
1. 禁止对 UnityEngine.Object 使用 ?? / ?.（fake-null 不参与空合并）；GetComponent 后 if (c == null) 再 AddComponent
2. 禁止在 Awake 缓存 DontDestroyOnLoad 单例引用；一律使用时解析
3. 禁止依赖组件 Awake 顺序；跨组件初始化一律懒加载 EnsureReady()
4. 禁止运行时 Shader.Find 创建正式材质；材质必须资产化 + 序列化引用
5. 运行时移除碰撞体：先 enabled=false 再 Destroy
6. 多层半透明面片必须显式 renderQueue，不得依赖默认排序
7. 状态变更只允许一个入口；输入路径与公开 API 复用该入口
8. 禁止用对象状态断言冒充可见性断言；可见性必须像素断言
补充：实现回调接口前先核对签名；写编辑器脚本前先 strings|grep 目标版本 DLL 确认 API 名
```

**编号速查**：`ENV-01~10` 环境工具链 ｜ `BUILD-01/02` 打包设备 ｜ `CODE-01~08`+`RENDER-01/02` 代码与渲染 ｜ `LOGIC-01`+`TEST-01/02/04` 逻辑与测试本身。明细见 `06` §2。

## 4. 文档构建规范

### 4.1 文档矩阵（一篇文档一个职责）

| 文档 | 职责 |
|---|---|
| `01_需求文档` | **唯一验收基准**（带稳定编号） |
| `02_开发环境文档` | 环境/版本/包名/第三方库的决策与证据 |
| `03_打包发布流程文档` | 傻瓜式打包、签名、混淆、上架 |
| `04_测试文档` | 分层测试、用例、**TC↔自动化映射**、准出标准 |
| `05_开发协作约定` | **流程宪法**：体检、提交、安全红线、沉淀约定 |
| `06_开发总结` | **黑匣子**：所有踩过的坑 + 三选一落点 |
| `07_玩法扩展评估` | **只评估不落地**的方案池与待决策项 |
| `08`（本文） | 跨项目方法论 |

原则：需求文档不写怎么打包，打包文档不写验收标准。

### 4.2 单一事实源 + 数字托管（本轮自动化）

**问题**：同一事实散落多处必腐化 —— 测试条数曾同时存在 99 / 73 / 实测 135 三个值；LFS 路径两处不一致。

**解法**：
1. 事实只在**一处台账**定义（版本/包名→`02`，测试条数→`04` §6.1，问题编号→`06` §2）；
2. **可被机器统计的数字交给机器**：文档中用 `<!-- STAT:NAME -->值<!-- /STAT:NAME -->` 包裹，`tools/stats.py` 统计真值并比对/回写；
3. 体检每次运行自动比对，过期即告警；`./tools/healthcheck.sh --sync-docs` 回写（回写后须提交）；
4. **叙述文字不重复硬编码这些数字**，改为引用台账。

> 落地效果：首次运行即检出 **11 处腐化值**并一次性修正。这是「让工具替人记住」的范本。

### 4.3 编号与引用纪律

- 需求条款用**持久化编号**（`§2.2-C`），里程碑后不重排；
- 新章节**追加到同类末尾**，禁止插中间导致编号位移；
- 「待确认/已确认」**就地更新状态标记**，不另起同名章节（本项目曾出现两组 §8.3）；
- 交叉引用写完整形式：`《01_需求文档》§2.2-C`，便于 AI 全文检索。

### 4.4 差距审计表（最值得复制的机制）

里程碑后拿实现逐条对照需求，四列缺一不可：

| 优先级 | 差距 | **需求出处** | 状态 |
|---|---|---|---|
| P0 | 提示系统零实现 | §2.2-F | ✅ 已实现（`HintService`） |
| P0 | 引导遮罩 `raycastTarget=true` 挡住操作 | §2.2-E | ✅ 已修复（+回归用例） |

> 没有「出处」列会退化成许愿池；本项目最后一天 5 次提交全部由这张表催生。

### 4.5 TC 必须能映射到自动化

写用例时同时写下「将来由哪个测试类覆盖」—— 避免僵尸用例，覆盖率可量化，AI 可照表补齐。见 `04` §6.1。

### 4.6 面向 AI 的可读性

绝对路径优先（`Assets/Scripts/Core/VoxelGrid.cs:41`）｜ 表格优先于散文 ｜ **结论必须带证据**（日志原文/实测重定向/代码引用）｜ 决策要记「为何否决」｜ 状态标记统一（✅/⏳/⚠️/❌/🚫）。

### 4.7 腐化自检清单（每里程碑）

- [ ] 出现 ≥2 次的事实是否一致？（版本/路径/条数）
- [ ] 是否有重复编号、失效引用？
- [ ] 手写汇总数字与明细是否一致？
- [ ] 是否有僵尸用例（无自动化也无执行记录）？
- [ ] 编号是否跳号？
- [ ] **`./tools/healthcheck.sh` 的统计台账是否全绿？**

## 5. 设计原则（六条）

| # | 原则 | 要点 |
|---|---|---|
| 1 | **分层硬边界** | Core（纯逻辑，仅依赖数学类型）/ Game（运行时）/ UI（不持有判定逻辑）/ Editor（不被运行时引用） |
| 2 | **接口先行 + 空实现** | `IAdService`/`NullAdService`、`ISaveStorage`、`ISfxPlayer`：逻辑层不被 SDK 阻塞，测试不依赖外部服务，测试还可注入内存实现规避共享状态污染 |
| 3 | **数据驱动** | 关卡（`LevelData`）、相机（`CameraConfig` 8 参数）、主题（`ThemeProfile`）、音频（`bgmKey`）全部配置化 —— 改内容/外观/手感零代码。**会被调的数值不许写死**（`snapAngle` 曾硬编码导致需求落空） |
| 4 | **状态变更唯一入口** | `AddAt/RemoveAt` 内完成「变更→重算→判定」，输入路径复用 |
| 5 | **懒加载 + 使用时解析** | 服务 `EnsureReady()`；单例引用使用时解析；不依赖 Awake 顺序（对应 A 类坑） |
| 6 | **性能预算前置** | 对象池、缓冲复用（零分配投影）、O(n) 判定、音效节流；预算数字在需求阶段写死 |

**附加**：文本一律走本地化 key（漏翻译会显示 key 本身，可被自动化验证）。

## 6. 扩展理念

### 6.1 表达力会被「静默压窄」（最重要的一条）

需求写「真 3D 体素空间」，实现里输入只产出 `(x,z)`、放置取该列最低空位 → 实际是「**高度图**」：无法悬挑/桥接/浮空，状态空间比宣称的小一个数量级。**测试全绿、游戏可玩，只有专门回头审计才会发现。**

**机制化对策**
1. **表达力审计**：里程碑收尾多问一句「玩家实际能构造的状态集合，是需求设想的那个集合吗？」
2. **可达性测试**：不只测「能否增删」，要测「能否构造出宣称的那类结构」；
3. 发现退化时**优先改实现**，不要悄悄改需求措辞蒙混过去。

### 6.2 判据：加约束 vs 加动词

> **「加约束」只能让游戏更难，「加动词」才能让游戏换玩法。**

| 轴向 | 治本度 | 例子 |
|---|---|---|
| 空间层（解锁表达力） | 最高 | 允许指定 y 放置、悬挑 |
| 系统涌现 | 最高 | 连通/支撑约束（让元素间产生因果关系） |
| 新动词 | 高 | 整体旋转/镜像、搬运模式 |
| 时间/风险（加失败条件） | 高 | 限步/限时挑战模式 |
| 模式/元层 | 高 | UGC 创作模式（绕过内容产能瓶颈） |
| 约束维度 / 信息控制 | 低~中 | 彩色匹配、三面投影、扫描揭示 |

**单调六根因自查表**：①空间维度不足 ②只有一个动词 ③只有一种约束 ④状态空间静态 ⑤无失败条件 ⑥信息完全公开。

### 6.3 容量约束与扩展点登记

- **每个新机制需 5~10 关「教 + 考」** → 10 关的体量最多承载 2~3 个机制；**先扩容量，再逐批引入**，每批配套教学关 + 考核关。
- 扩展前先列「**改一处要动哪些文件**」清单（`07` §8）。价值：影响面变成审阅对象；本项目借此发现「整体旋转在判定层免费，但仅正方形平台成立」这类硬约束。
- **内容用远程资源包下发**：新章节 = 新数据包，无需发版。配套要求：反射类型、按地址加载的类型必须进**剥离白名单**，否则开启代码剥离后运行时才崩 —— 且这类崩溃**只在正式包出现**（联调包默认不剥离）。
